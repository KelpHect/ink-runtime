# A13 — Inkling 2 Mini ecosystem: what exists and what to steal

Scope: `thinkingmachines/Inkling-2-Mini` (released 2026-11-20, Apache-2.0), arch `inkling2_loop`, single ~19.5 GB safetensors checkpoint in mixed NVFP4 (expert layers 0–19) + MXFP8 (layers 20–23) + BF16, plus a bundled 636 MB `mtp.safetensors` DSpark drafter. Surveyed ~25 sources: HF model repo + community tab, HF blog, transformers/vLLM/SGLang/llama.cpp/mlx-lm PRs, Unsloth docs + GGUF repos, TokenSpeed/LightSeek, tml-renderers, and a dozen community engine forks and benchmark threads.

**Bottom line:** there are *four* independent, permissively-licensed reference implementations worth mining — HF `transformers` (canonical math, Apache-2.0), `llama.cpp` (`src/models/inkling2-loop.cpp`, C/C++ ggml, MIT-ish), `vllm/models/inkling2/` (production CUDA/Triton, Apache-2.0), and `sglang/python/sglang/srt/models/inkling_common/` + model file (Apache-2.0). Additionally, GPTQModel did a documented clean-room port with fused W4A16/W8A16 Triton GEMMs that decode the packed NVFP4/MXFP8 formats without materializing BF16 weights — the single most relevant prior art for our runtime. The community has already mapped every trap: the NVFP4 scale layout, the per-pass KV explosion, the loop-slot weight sharing, the DSpark draft tap points, and Metal/AMD/Vulkan gaps.

## 1. The checkpoint and on-disk formats

- Repo `thinkingmachines/Inkling-2-Mini` is **14 files, 20,191,643,294 bytes**: `model-00001-of-00001.safetensors` (19.5 GB), `model.safetensors.index.json` (109 kB), `mtp.safetensors` (636 MB DSpark draft), `hf_quant_config.json` (67.9 kB, **modelopt** quant manifest), `config.json`, `generation_config.json`, `chat_template.jinja`, `processor_config.json`, `tokenizer.json` (26.2 MB), `tokenizer_config.json`, `special_tokens_map.json`, plus tiktoken assets. Source: <https://huggingface.co/thinkingmachines/Inkling-2-Mini/tree/main>
- NeMo's model page pins the architecture: 24 decoder layers, hidden 2304, loop = layers 6–17 ×3 passes (48 layer visits), 24 Q / 8 KV heads, head dim 128, attention pattern "5 local + 1 full" ×4 (local window 1024, causal), 128 experts top-8 sigmoid routing with routing scale 8, expert intermediate 1152, vocab 201,024 rows / 200,058 usable, logit soft cap 30, 23-layer ViT (hidden 1024, 16 heads) with native 20×20 patches and 2×2 neighbor merge. "5B active counting every pass" (HF blog says ~3B/3.4–3.5B per pass; model card: each extra loop pass adds ~1.0B effective → 5.4B effective at 3 passes). <https://docs.nvidia.com/nemo/automodel/model-coverage/vision-language-models/thinkingmachines/Inkling-2-Mini>
- **NVFP4 layout** (verified by ModelCloud's kernel work): `value = e2m1(code) * e4m3(block_scale) * fp32_global_scale`; two codes per byte, *even column in the low nibble*; one E4M3 scale per 16 contiguous columns; one FP32 scale per expert (experts are stored as 3-D stacked `gate_up_proj`/`down_proj` tensors → "per-expert scales"). **MXFP8**: `value = e4m3(byte) * 2^(e8m0 - 127)`; one E8M0 scale per 32 columns. Decoding all experts to BF16 costs ~49 GB. <https://github.com/ModelCloud/GPTQModel> commits `4682e21`, `c6cb9c8` (referenced from <https://github.com/huggingface/transformers/pull/51050>)
- **Marlin cannot decode this NVFP4 layout**: `dequant_fp8_scales` pairs adjacent groups into one 16-bit slot selected by per-warp row parity; for these tile shapes every odd group reads zero (measured 0.535 agreement vs FP64 oracle — exactly 8 of 16 columns). This is why naive vLLM/quants fail silently. GPTQModel's fix: Triton GEMM decoding the weight tile inside the K loop (`nvfp4_w4a16_linear`, `mxfp8_w8a16_linear`), activations BF16/FP16, FP32 accumulate, no tl.dot_scaled/SM100/CUTLASS/Marlin — portable to everything. Rel. Frobenius 1.66e-3 vs oracle.
- Weight-key renames the checkpoint needs (from GPTQModel notes): `.attn.` → `.self_attn.`, `wq_du` → `q_proj.linear`, plus `wo_ud`, `wk_dv`, `wv_dv`, `gate_attn`, `rel_logits_proj`, `q_l2_clip`; loop-config fields are flattened in config.json. Their clean-room port loads 1244/1244 tensors, ~17.6 GB packed, forward finite on CPU and CUDA (18.2 GiB BF16 activations).

**transformers notes** (from the PR + benthecarman's test): dequantizes NVFP4/MXFP8 to BF16 on load (prints a misleading "Unknown quantization type, got modelopt" warning — dequant is real: rel err 0.0025 on `down_proj` L0, 0 on L23); attention is **eager-only** (every layer adds learned relative-position bias + a sink); `causal_conv1d` is an unlisted optional dep for the fast short-conv kernels else slow PyTorch fallback; cache has **one entry per layer visit (48)**; `output_hidden_states`/`output_attentions` return per-visit entries; `loop_num_passes`/`loop_share_cache` apply only to the varloop checkpoint `TML-d24-varloop-research`. <https://huggingface.co/docs/transformers/main/en/model_doc/inkling2_loop>

**vLLM implementation details worth stealing** (blog + PR): each pass's KV cache and conv-state cache are registered as ordinary per-layer caches — prefix caching and CUDA graphs need zero new machinery. Message reads: all four messages of a layer (q/k/v/MLP inputs) fetched in **one attention-residual kernel**; the four rank-64 controllers' weights stacked so down/gain/forget projections run as **batched GEMMs**; one Triton kernel computes controller RMSNorms; another fuses the gated merge with the following sublayer's RMSNorm — **in FP32 without FMA contraction to match reference bit-numerics**. Sublayer fusion (allreduce + short-conv + residual + attn-residual + RMSNorm in one kernel) generalized from hidden 4608→2304 with a mode returning the FP32 mix pre-norm; TP>1 fuses NVLink-multicast allreduce. NVFP4 MegaMoE **zero-pads intermediate 1152→1280**. Verified HW: SM100/SM103, SM90 (H100/H200 — with expert-GEMV narrow-K fix + tuned small-batch Marlin GEMV + FP32 one-shot MoE combine), SM120/121 (DGX Spark). **SM86/SM89 unsupported** upstream (Ampere/Ada need community ports). Perf on GB200 (forward only): decode step batch-1 = 1.51/2.67/3.85 ms for 1/2/3 passes → ~260 tok/s; batch-32 8.11 ms. KV capacity 352K/233K/175K tokens for 1/2/3 passes; `loop_share_cache` gives 194K (conv states stay per-pass). GSM8K 97.0% with DSpark. <https://vllm.ai/blog/2026-11-20-inkling2-mini>, <https://recipes.vllm.ai/thinkingmachines/Inkling-2-Mini>

**SGLang PR #51926 specifics**: registers `Inkling2LoopForConditionalGeneration`/`inkling2_loop`, treats it identically everywhere Inkling2 is special-cased (MTP/DSPARK draft setup, chat encoding, parser defaults, CUDA-graph/PD/override hooks); **fused loop message controllers**, with the controller mix **pipelined over column tiles for long prompts**; `--inkling2-loop-num-passes`/`--inkling2-loop-share-cache` (varloop only). Run line: `--attention-backend fa4 --bf16-gemm-backend torch --dtype bfloat16 --tp 1 --page-size 128 --grammar-backend xgrammar` (+`--speculative-algorithm DSPARK`); HF blog says "prerequisite: run it on SM103".

## 3. TokenSpeed — what it is

Not TML's runtime: **TokenSpeed is the LightSeek Foundation's open-source (MIT) inference engine** — "speed-of-light LLM inference engine designed for agentic workloads, TensorRT-LLM-level performance with vLLM-level usability" (<https://github.com/lightseekorg/tokenspeed>, <https://lightseek.org/blog/lightseek-tokenspeed.html>). Architecture: **C++ control plane** (scheduler as a finite-state machine; KV-cache ownership/overlap timing enforced by the type system at compile time) + **Python execution plane** + **Rust entrypoint** (SMG and Dynamo drive the engine over msgpack — no Python on the request path). Kernels are a first-class pluggable subsystem behind a portable public API + central registry (`tokenspeed-kernel` portable Triton, `-amd` Gluon, `-npu`, `-mla` with one of the fastest MLA decode impls on Blackwell). They partnered with TML for Inkling day-0 (NVFP4 on B200/B300, MXFP4 on MI350X/355X — `lightseekorg/Inkling-MXFP4`) and Inkling 2 Small day-0 (476 tok/s/user decode on 4×B300 agentic replay; `ts serve --speculative-algorithm DSPARK`, `inkling2` reasoning parser; images preprocessed in the Rust gateway byte-for-byte with TML's processor). Recipes: <https://lightseek.org/tokenspeed/recipes/models>. For us: it's the closest public model of a **split control/execution-plane Rust+C++ engine**, and its kernel-API boundary is exactly the shape our runtime needs. NVIDIA Dynamo is the serving layer TML lists alongside it (TokenSpeed already uses Dynamo's SMG wire).

## 4. GGUF ecosystem — who converted what, and how

- **ggml-org/Inkling-2-Mini-GGUF** (official): BF16 52.2 GB (NVFP4+MXFP8 upcast), Q8_0 27.8 GB, **IQ4_NL 17.6 GB** (imatrix on bartowski's v6 calibration data rendered through the chat template; NVFP4 experts `ffn_gate_up_exps`/`ffn_down_exps` of layers 0–19 → IQ4_NL, **everything else Q8_0**, loop-controller weights stay F32); mmproj BF16 642 MB / Q8_0 346 MB. KLD vs BF16 on wikitext-2: Q8_0 0.0030 (97.6% same-top), IQ4_NL 0.0095 (95.5%). Also `ggml-org/TML-d24-varloop-research-GGUF` (experimental). <https://huggingface.co/ggml-org/Inkling-2-Mini-GGUF>
- **unsloth/Inkling-2-Mini-GGUF** — the interesting one. UD ("Unsloth Dynamic") files **keep native NVFP4 tensor blocks in the GGUF**: one teardown found **40 nvfp4 tensors + 154 q8_0 + 32 bf16** inside UD-Q4_K_XL. `UD-Q8_K_XL` (22.87 GB) = lossless reference: original NVFP4 experts kept, MXFP8 upcast. `UD-Q4_K_XL` (17.63 GB, recommended): NVFP4 experts largely kept, MXFP8 experts → Q8_0; KLD 0.0107 / 98.0% top-token. Full ladder: IQ1_S 7.76 / IQ1_M 8.02 / IQ2_XXS 8.49 / Q2_K_XL 9.14 / IQ3_XXS 11.66 / Q3_K_XL 13.63 / IQ4_XS 15.73 / Q4_K_M 16.61 / Q4_K_XL 17.63 / Q8_K_XL 22.87 GB (KLD 0.0911→ref, top-token 89.4%→98.0%). Plus `mmproj-F16.gguf` (639 MB), `dspark-Inkling-2-Mini-Q8_0.gguf` (504 MB) and a `_Old` padded-vocab variant (402 MB). **Two on-disk layouts exist**: root files use Unsloth's "looped-layer layout" (their builds only); `Mainline_Support/*.gguf_file` files are mainline-compatible (early files wrote `block_count=48` with 24 physical → load failure, fixed ~2026-11-23). <https://huggingface.co/unsloth/Inkling-2-Mini-GGUF>, <https://unsloth.ai/docs/models/inkling-2-mini>
- So conversion is **dequantize-then-requantize per tensor class**: ggml-org upcasts NVFP4→BF16 then requantizes (IQ4_NL for experts), Unsloth preserves NVFP4 blocks verbatim (needs `nvfp4` ggml type + per-expert scales — supported on CUDA/HIP, NOT Metal mainline) and dequantizes MXFP8→Q8_0/BF16. Community "no-NVFP4" files exist for Metal (e.g. InterpreticAI IQ3_XXS 11.75 GB).
- Other quant repos: **bartowski** (`bartowski/thinkingmachines_Inkling-2-Mini-GGUF`, b12600 imatrix: bf16 52.23, Q8_0 27.82, Q6_K_L 25.36, Q6_K 24.70, Q4_K_M 18.66 GB); **AtomicChat/Inkling-2-Mini-GGUF** (merged-layout Q8_0 27.7 GB + DSpark Q8_0 + A100 numbers); **Xylolabs** (Unsloth per-tensor types, own imatrix); **mradermacher** (not found as of 11-24); **Tech2wild/Inkling-2-Mini-W4A16** (INT4 weight-only 16.47 GB + 0.64 GB drafter for the Ampere vLLM overlay — "no GPTQ/AWQ/AutoRound possible pre-transformers, so calibration-free"); **infosave/Inkling-2-Mini-cmf** (`Inkling-2-Mini-q4tp.cmf` 15.12 GB single file); **Wa1k3r/…NVFP4exp-Q8-draft-LexiSuite** (RDNA); **Sadanie/Inkling-2-Mini-Half** (MS-MoE sparse-load 9 GB); mlx-community 4-bit + oQ4e-mtp.

## 5. llama.cpp specifics — mapping inkling2_loop onto ggml

- The port **expands the 24 physical layers into 48 "loop slots" at load** — i.e. it duplicates the shared core weights per pass rather than running a true loop. Consequence: **PR #32704 bug** — slots were copied *before* scale tensors attached, so passes 2–3 ran NVFP4 experts with no per-expert scales → gibberish (PPL 130.43 vs 7.65) on files with native NVFP4; ggml-org files unaffected (they contain no NVFP4). For our runtime this is the canonical argument for **true weight-sharing with per-visit state**, not slot copies.
- KV + conv state: **one cache per layer visit → 48 KV caches + 48 conv-state caches; ~16.6 MiB per 1K tokens** (F16). A 14–16 GB KV cache at 128–256K ctx is the #1 user complaint; "share KV across passes" exists only in the varloop checkpoint (`loop_share_cache`). Conv states must stay per-pass regardless.
- New/extended ops used: NVFP4 `mul_mat_id` (CUDA yes, **Metal returns false → CPU fallback**, ~10 t/s on M2 Max/15.5 t/s M6 mini vs 33.6 t/s for a no-NVFP4 file); "banded attention" for sliding-window+full mix; `n_tokens_banded_min = 32` small-batch fast path in `inkling2.cpp` (forcing it off made decode 40–55% slower — keep the banded path); short convs via ggml conv ops; loop message gates are small F32 GEMMs.
- Expert offload traps: `--n-cpu-moe` counts *layer visits* (…=14 puts 30 of 48 expert runs on CPU); correct pattern is `-ot "blk\.(0-5|18|19|2[0-3])\.ffn_.*_exps\.=CPU"` keeping **loop layers 6–17 experts on GPU**. `--fit` doesn't know about the loop either.
- DSpark: `--model-draft dspark-…-Q8_0.gguf --spec-type draft-dspark --spec-draft-n-max 2 --n-gpu-layers-draft 99`. Draft is a 3-layer model reading target hidden states at **layer visits 5, 23, 41 + final norm (index 48)**; **needs exactly k=7 proposals in vLLM, depth-2 optimal in llama.cpp** (3rd token rarely accepted; acceptance ~0.32–0.38 at temp 1.0 on a 5090; higher greedy). Draft GGUF uses `markov_w1` tensors + a recurrent/"confidence" head — early mainline rejected the drafter on a shape mismatch (PR #32218-era patch). Unsloth ships both padded-vocab and mainline layouts.
- Bugs already fixed upstream: #32755 garbage output with looped experts on CPU (AMD) → #32807; open: #32710 perplexity NaN on CUDA, #29782 Mac perf-core thread default, Vulkan compute-buffer OOMs (`-ub 48` workaround), Vulkan blowup with Q8_K_XL.

## 6. NVFP4 on non-Blackwell — what actually happens

- **vLLM upstream: fails.** Verified only SM90/100/103/120/121; Ampere/Ada kernels gated behind capability checks (TMA, PDL, FP8 KV hardware conversion, block-scale GEMM).
- **Working community Ampere port**: [Hiutaky/vllm `ampere-port`](https://github.com/Hiutaky/vllm) (doc `INKLING2-RTX3090.md`, all changes in `vllm/models/inkling2`): PDL gated to SM90+, no TMA below SM90, Triton fallback for `conv_mix`, FA2 for the vision tower, min capability 80, **E4M3 FP8 KV emulated in software** (Ampere lacks the cvt instruction), DSpark works (k=7 mandatory, draft KV stays BF16), `embed_tokens` CPU-offloaded. RTX 3090 24 GB: **91 t/s decode, 112–147 with DSpark** (reporter #2: ~90→64 t/s as ctx fills to 197k), ~2,500–2,700 t/s prefill, 128k–256k ctx, KV pool 207k tokens/8 seqs, weights 17.55 GiB on-GPU. <https://huggingface.co/thinkingmachines/Inkling-2-Mini/discussions/20>
- **AMD/RDNA**: llama.cpp HIP/Vulkan ~30 t/s on RX 7900 XTX (with #32704 patch pre-merge); a "CUDA/HIP fusions" PR claims 31→54 t/s on RDNA4; **LexiSuite** (bare-metal Rust engine) reports **130 t/s with draft / 2,148 t/s prompt** on one 7900 XTX, 524k ctx at 767 t/s prompt, 10/10 needle. Unsloth ships ROCm builds for gfx120X/1151/110X/103X/90a/908; Ryzen AI Max (gfx1151) does 32.8 t/s (Linux). SGLang AMD PR #52751 open; TokenSpeed does MI350X+ only.
- **Apple**: mainline Metal can't run NVFP4 expert matmuls (CPU fallback → 10–15.5 t/s); Unsloth's build has Metal NVFP4 kernels; MLX PR #2086 hits ~32 t/s gen/~1,500 prefill on M3 Ultra (pipeline-parallel impossible — loop spans stages); **MTPLX 2.13** 128.8 t/s on M5 Max; **exo** claims 210 t/s M5 Ultra (unreleased); oMLX community quant + draft. Intel Arc Pro B70 works via a vLLM plugin (~57/76 t/s).
- **Intel/other**: SYCL build thread exists; PolyStrata PR simplexai-labs/PolyStrata#200 runs a 12 GB RTX 3060 at 35 t/s TG/800 prefill after a CUDA prompt-attention fix.

## 8. Reported issues / UX traps

- Endless reasoning loops / "stuck repeating actually let me act" (HF disc #7, #45, #48; unsloth #22; model card itself warns: set output-token limits — looped compute invites re-checking spirals; also temp-0 repeats).
- Tool-calling edge: model writes a lead-in sentence then ends turn without emitting the call (HF disc #21); "over-writing" bash commands reported on Reddit/HF (#16).
- "Dinosaur problem" (disc #15, 13 replies) and quality quirks vs Qwen3.8-27B — consensus: stronger on code, weaker writing/knowledge recall.
- LM Studio multi-GPU `CUDA0 error` loading Q8 (disc #13); Ollama Apple-only so far; "not available in your region" complaints on HF inference providers (region gating, #10/#34).
- `vLLM W4A16?` thread (disc #4) + both Ampere recipes confirm: **no stock vLLM on SM86/89**; and no GPTQ/AWQ quantization flow existed at launch (transformers impl + activation capture needed; GPTQModel has since added `inkling2_loop` → `Inkling2LoopQModel` with Defuser 0.0.33 for the 3-D expert container — so offline GPTQ is now possible).
- SGLang on SM120: `fa4` requires `K.dtype == Q.dtype` (BF16 KV needed); the `lmsysorg/sglang:inkling-2-mini` image exists.
- Memory: 20 GB weights + 16.6 MiB/1K KV; 32 GB Mac/VRAM is the realistic floor, 24 GB uncomfortable for full precision.

## 9. tml-renderers / Tinker — official-format hints

`tml-renderers` 0.4.2 on PyPI (<https://pypi.org/project/tml-renderers/>): "Public TML chat types, tokenizers, and native renderers" — a **compiled extension** (needs torch ≥2.11) that renders structured text/image/audio chat into model-ready tokens + media spans, for training and inference. Renderers: `Inkling`, `Inkling2` (both TMLv0 grammar — covers Mini; no Mini-specific class) plus Qwen3/3.5/3.8, DeepSeek V3→V4.1, Kimi K2→K3.1, GLM 5.2/5.3, GPT-OSS, Nemotron 3/3.5 VL. API: `render_for_completion` (prompt + streaming parser), `render_for_sft` (aligned per-token loss weights), `bridge_to_next_turn` (append turns onto the exact sampled token prefix without re-render), `parse_stream` incremental parsing. This is the **authoritative spec of the wire format**, not inference internals — but it tells us exactly what the playground/Tinker emits: TMLv0 message framing (`<|message_system|><|content_text|>…<|end_message|>`, `<|message_user|>`, `<|message_model|><|content_thinking|>`, `tool_declare` + `<|content_xml|>`, image token `<|unused_200054|>`), reasoning effort injected as a system text `Thinking effort level: 0.9` (levels none 0.0 / minimal 0.1 / low 0.2 / medium 0.7 / high 0.9 / xhigh·max 0.99). bartowski's card prints the same prompt format. `chat_template.jinja` + `processor_config.json` in the repo are the other two canonical refs. Tinker Cookbook + Miles/SkyRL docs cover the post-training side.

## 11. What to steal (ranked)

1. **transformers `modeling_inkling2_loop.py`** — canonical math for loop/message gates/block attention residuals/convs; pair with `modular_` to see what's inherited from inkling2.
2. **GPTQModel's `nvfp4_w4a16_linear` / `mxfp8_w8a16_linear` Triton GEMMs + their checkpoint-key rename map** — decode-on-the-fly, no dense materialization, no SM100 gate. Direct template for our NVFP4 path. (Their Marlin-defect writeup is required reading.)
3. **vLLM `vllm/models/inkling2/`** — per-visit-caches-as-normal-layers trick (prefix caching/CUDA graphs for free), fused 4-message read + batched rank-64 controllers, FP32-no-FMA gated merge fused into RMSNorm, 1152→1280 MegaMoE padding, `--cpu-offload-params embed_tokens` trick.
4. **llama.cpp `inkling2-loop.cpp` + `conversion/inkling2.py`** — C-land mapping: banded-attention fast path, `n_tokens_banded_min`, conv-state layout, `-ot` expert-offload semantics, and the #32704 lesson (don't share-by-copy; share-by-reference and attach scales once).
5. **Unsloth's Metal/HIP NVFP4 mul_mat_id + banded-attention-for-non-F16-KV patches** (unslothai/llama.cpp #396/#399, releases b12631/b12649-mix) — the only public source for NVFP4 experts on Metal.
6. **DSpark specifics**: draft taps visits 5/23/41 + final norm; k=7 (vLLM) / depth-2 sweet spot (llama.cpp); acceptance collapses at temp 1.0 on long ctx — our engine should gate speculation on acceptance telemetry. `markov_w1` + confidence/recurrent head inside `mtp.safetensors`.
7. **tml-renderers TMLv0 + chat_template.jinja** — byte-exact prompt/tool/reasoning framing.
8. **Varloop knobs** (`loop_num_passes`, `loop_share_cache`) — the community immediately wants them on the fixed model; vLLM measured shared-KV saves less than a dropped pass (conv states dominate). Design our loop scheduler to allow both.
